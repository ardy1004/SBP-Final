## Hydration #418 — Meta in-app-browser injection (closed investigation, still active in production)

- 🔥 **Hydration #418 BELUM tertutup, dan tidak bisa ditutup.** `6ff9824` mencabut PEMICU milik kita (snippet Meta Pixel), bukan KERAPUHANNYA. Script pertama dokumen tetap `<script type="application/ld+json">` milik `<Meta />`, jadi penyisipan node apa pun di depannya tetap merusak. Diukur ke produksi 2026-08-31: tanpa injeksi **0 error**, dengan satu script pihak ketiga ber-`insertBefore` **10 × #418**.
  - Pemicunya sekarang **in-app browser Meta**, yang menyuntikkan JS-nya sendiri ke halaman. Dari 35 baris #418: **29 dari `FBAN`/`FBAV`/`Instagram`** (17 Android, 18 iPhone), **33 punya `?fbclid=`** (klik iklan). Didukung 5 baris `postMessage: Java exception` (jembatan JS Android WebView) dan 8 `Script error.`. Bukti langsung skema injeksinya ada di data: baris `window.onerror` ber-`filename: "iabjs://navigation_performance_logger_android"`.
  - **Di luar kendali kita** — tidak ada cara bersih membuat `<head>` yang dihydrate React kebal terhadap injeksi pihak ketiga. Yang dilakukan: laporan ditandai `context.in_app` (`browserInApp()` di `entry.client.tsx`) dan Admin → Errors **menyembunyikannya secara bawaan** lewat filter `jenis` (`app`/`in_app`/`all`). Barisnya TIDAK dihapus — kalau polanya berubah atau menyebar ke browser lain, harus tetap bisa dilihat.
  - 🔥 **DAFTAR PENANDA IN-APP ADALAH ALLOWLIST YANG BASI DIAM-DIAM — satu sumber di `functions/_lib/inAppBrowser.js`.** Pada 2026-09-01 Admin → Errors menampilkan 41 baris #418 **padahal filter "Sembunyikan in-app browser" menyala**: 44 dari 49 baris yang lolos berasal dari **Threads**, yang UA-nya memakai token **`Barcelona`** (nama kode internal aplikasinya — kata "Threads" TIDAK pernah muncul). Penanda `IABMV` (*In-App Browser Meta Version*) ikut ditambahkan untuk varian iOS. Diukur ke produksi: baris belum-ditinjau yang lolos **50 → 5** (sisanya 4 `[scheduler]` + 1 Chrome desktop), tersembunyi 449, dan 5+449 = 454 = total (aritmetika rekonsiliasi).
    - **Yang membuatnya luput: daftarnya ditulis DUA KALI** — regex di `entry.client.tsx` dan rangkaian `LIKE` di `errors/index.js`. Sekarang keduanya mengimpor `PENANDA_IN_APP` dari `functions/_lib/inAppBrowser.js` (pola yang sama dengan `viralframe-shared.js`: backend impor natif, frontend lewat Vite). Menambah penanda berikutnya = **satu baris di satu file**.
    - **Pemicunya penempatan iklan, BUKAN posting organik kita.** Posting Threads sendiri sudah 5–12/hari sejak 24 Agu tanpa memicu apa pun; yang meledak justru saat tayangan melonjak 76–158/hari → 479–637/hari dan **39 dari 44** baris membawa `fbclid`. Artinya: **setiap penempatan iklan baru berpotensi memunculkan kanal in-app baru yang lolos filter**, dan gejalanya bukan error melainkan "kebisingan yang tiba-tiba lolos". Kalau itu terjadi: baca `user_agent` baris-barisnya, cari token aplikasinya, tambahkan.
    - Karena filter mencocokkan `user_agent` yang tersimpan, **penanda baru berlaku surut ke baris lama tanpa migrasi**.
  - **Halaman Admin → Errors menampilkan jumlah yang DISEMBUNYIKAN** (mis. `5 belum ditinjau · 449 disembunyikan sebagai in-app`). Tanpa itu lonjakan Threads dari 1/hari ke 26/hari tidak terlihat sebagai lonjakan — layar hanya menghitung yang lolos filter, jadi kanal Meta berikutnya akan luput dengan cara yang sama persis. Dihitung lewat agregasi kondisional dalam query `COUNT` yang sudah ada (`SUM(CASE WHEN … THEN 0 ELSE 1 END)`), jadi **nol round-trip D1 tambahan**.
  - **Retensi tabel — semuanya menumpang `bersihkanTabel()` di cron `purge-trash`** (03:10 WIB), jadi menambah retensi baru = satu blok di satu fungsi, nol perubahan worker: `error_logs` 30 hari · `viralframe_scheduled_posts` yatim 30 hari · **`property_view_daily` 180 hari** · **`viralframe_caption_history` 90 hari**. Periode dipilih dari pembaca terpanjang masing-masing: `property_view_daily` hanya pernah dibaca 30 hari (margin 6×), `caption_history` hanya 12 baris terakhir. ⚠️ `property_view_daily` memakai kolom `tanggal` (TEKS WIB), bukan `created_at` — pakai `sqlTanggalWibMinus()`, jangan tulis ekspresi tanggal sendiri.
  - **Retensi `error_logs`: 30 hari, menumpang cron `purge-trash`** (03:10 WIB). Tabelnya sebelumnya tidak punya pembersih sama sekali — endpoint `DELETE /api/admin/errors?older_than_days=` ada sejak lama tapi **nol pemanggil** — sementara in-app browser menyumbang ~250 baris/hari. ⚠️ Housekeeping-nya (`bersihkanTabel()`) sengaja dipisah jadi fungsi dan dipanggil **sebelum** jalur purge aset: jalur itu punya DUA `return` awal, jadi kalau ditulis inline di bawahnya ia hanya jalan pada malam yang kebetulan ada sampah — pembersih yang diam-diam tidak pernah jalan.
  - ⚠️ **Sudah DISINGKIRKAN sebagai sebab — jangan diuji ulang:** `fbclid` bocor ke HTML ter-cache (HTML untuk `fbclid=AAA` dan `=BBB` **identik byte-nya**, canonical & og:url bersih), cache HIT (HIT + fbclid + UA Meta → 0 error), dan UA sniffing di SSR (tidak ada sama sekali).
- ✅ **`Cannot read properties of undefined (reading 'startTime')` di `et.reportAllChanges` BUKAN kode kita — JANGAN diselidiki ulang** (ditutup 2026-09-04). Pelakunya **beacon Cloudflare Web Analytics**, yang disuntikkan Cloudflare **di edge SETELAH HTML kita dibuat**. Buktinya empat: (a) nol `web-vitals`/`reportAllChanges` di seluruh `src/` + `functions/` + `package.json`; (b) `static.cloudflareinsights.com/beacon.min.js` memuat `reportAllChanges` **16×** dan `startTime` **51×**; (c) browser bersih tanpa ekstensi (Playwright headless) = **0 error** tersebut; (d) `SELECT COUNT(*) FROM error_logs WHERE message LIKE '%startTime%'` = **0**.
  - ⚠️ **`curl` polos TIDAK melihat beacon-nya** — Cloudflare hanya menyuntikkan bila request terlihat seperti browser (UA + `Accept: text/html`). Jadi "tidak ada di HTML kita" bukan bukti tidak dimuat; ukur dengan browser sungguhan (`page.on('request')`), bukan grep HTML. Kesalahan baca ini yang membuat script pihak ketiga mudah luput dari audit.
  - Sebabnya beacon membaca `entries[entries.length-1].startTime` di `requestIdleCallback`; kalau `PerformanceObserver` belum punya entri, larik itu kosong. Yang hilang cuma satu titik data analitik. Kalau ingin bersih: matikan **Web Analytics** untuk domain ini di Dashboard Cloudflare — keputusan produk, bukan perbaikan kode.
- **`"Importing a module script failed."` di `error_logs` = tab lama saat deploy, bukan bug.** React Router memuat chunk route secara lazy dengan nama ber-hash; setiap deploy mengganti hash-nya, jadi tab yang sudah terbuka gagal memuat chunk yang sudah tidak ada. Obatnya hard reload. Muncul berkelompok tepat pada hari dengan banyak deploy — **jangan diperlakukan sebagai regresi**, dan ingat: setelah deploy, uji manual WAJIB dengan hard reload atau yang diuji justru bundle lama.

## Diagnostic methodology + check:hydration mechanics

(Konteks: prohibition-nya — "JANGAN pernah menyisipkan node ke `<head>`/`<body>` dari script inline yang berjalan SEBELUM React hydrate" — tetap ada di root CLAUDE.md. Bagian ini detail cara mendiagnosanya.)

- Kenapa hanya sebagian halaman: yang kena hanya yang punya `script:ld+json` dari `<Meta />` (`/`, `/properties`, `/faq`, detail properti, `/blog/<slug>`), karena di situlah script pertama dokumen adalah milik React. Halaman tanpa JSON-LD lolos — jadi **cakupan yang tidak merata bukan berarti bukan penyebabnya**.
- **Cara mendiagnosis hydration**: `npm run dev` lalu buka halamannya — React mode DEV menyebut elemen persisnya; produksi hanya memberi nomor error. `/faq` reproduksi minimal terbaik (tanpa loader, tidak butuh D1). ⚠️ Dev TIDAK merender pixel/gtag (loader jatuh ke `TRACKING_FALLBACK` tanpa D1), jadi suntikkan snippetnya lewat `page.route` untuk mereproduksi. ⚠️ Memblokir jaringan (mis. `connect.facebook.net`) **bukan uji kendali yang sah** — script inline tetap menyisipkan node walau file gagal dimuat.
- **Pemantau hidrasi runtime ada di `src/app/entry.client.tsx`** (bukan `root.tsx`: error hidrasi terjadi selama `hydrateRoot()`, sebelum `useEffect` mana pun jalan) dan mengirim ke `/api/client-error` → Admin → Errors. Dua kanal: `onRecoverableError` (kait resmi React) **dan** penyadap `console.error`. Diukur 2026-08-30 pada build produksi: **`console.error` selalu menang** karena React DOM memanggil penangan hidrasi React Router yang menulis ke sana lebih dulu; field `context.jalur` mencatat kanal mana yang menyala.
  - ⚠️ **JANGAN menunda laporan `console.error` demi "memenangkan" `onRecoverableError`** (yang membawa `componentStack`). Sudah dicoba: `setTimeout` 0 ms tidak mengubah apa pun, dan 50 ms membuat laporannya **hilang sama sekali** (1 → 0 terkirim). Menukar keandalan pelaporan dengan satu field diagnostik bukan pertukaran yang sehat.
  - ⚠️ **Uji perubahan pemantau ini dengan build PRODUKSI** (`npm run build` + `wrangler pages dev dist/client`), bukan `npm run dev` — mode dev memakai jalur peringatan yang berbeda sehingga hasilnya menyesatkan.
- `check:hydration` (`scripts/check-hydration.mjs`) membuka 7 halaman publik dengan Playwright dan **GAGAL bila ada error hydration**. Smoke TIDAK bisa menangkap ini — halaman yang hydration-nya runtuh tetap membalas HTTP 200 dengan HTML lengkap; rusaknya hanya terlihat di console browser. Dua halaman kontrol tanpa JSON-LD ikut diuji: kalau SEMUA merah, curigai script/jaringan lebih dulu, bukan aplikasinya. ⚠️ Penjaga ini **membuang cache lewat param acak** — tanpa itu ia menguji HTML basi (TTL edge 300 detik) dan melaporkan hasil yang salah tepat setelah deploy.
  - Punya **pemeriksaan STATIS** juga: HTML kita sendiri dilarang memuat `insertBefore` / `getElementsByTagName('script')`. ⚠️ Batasnya tegas — penjaga hanya melihat HTML yang KITA kirim; **injeksi oleh browser pihak ketiga tidak terjangkau**. Lulus = "kita tidak menembak kaki sendiri", BUKAN "kebal".
  - ⚠️ **Wajib punya ASERSI POSITIF, bukan cuma menghitung error** (ditambahkan 2026-08-30). Versi pertamanya LULUS pada halaman yang tidak hydrate sama sekali — dibuktikan dengan menyajikan HTML produksi dari server lokal yang aset JS-nya 404: nol error, verdik hijau, React tidak pernah jalan. Sekarang penjaga memeriksa React benar-benar memasang properti fiber (`__reactFiber$…`) pada DOM; **"tidak ada error" bukan bukti sehat.** Ini persis kegagalan yang paling mungkin terjadi di sini karena hash manifest server/klien bisa tidak sinkron tanpa clean build.
  - Menunggu **4,5 detik**, bukan 3: pemuat gtag/GTM tertunda menyisipkan `<script>` pada detik ke-4, dan penyisipan node persis itulah yang dulu merusak hydration — menunggu 3 detik menaruhnya di luar jendela pengamatan.
